## 3. Factors, levels and setups

| Factor | Levels |
| --- | --- |
| Embedder | Qwen3-Embedding 0.6B, 4B, 8B (Zhang et al. 2025) |
| Chunk size | 512, 1,024, 2,048 Qwen3 tokens; overlap 15% (77, 154, 307 tokens) |
| Reranker | Off, Qwen3-Reranker 0.6B, 4B, 8B (llama.cpp `/v1/rerank`) |
| Hybrid | Off (dense only), or BM25 plus dense with RRF fusion |

- **Chunk.** In this file a "chunk" is a stored chunk: one row of the index, as written at ingest. Unit scoring, the 100-chunk depth, `evidence_recall_20k` and the token cut all use the ranked list of stored chunks and each chunk's own token count. Why: how often OMRS context assembly merges neighbouring chunks depends on chunk size, so a merged row would confound the factor that H6, H7 and H8 test. OMRS gets one additive search option that returns the ranked stored chunks with no context assembly. Its default is off, so the product does not change.
- **Search stage.** Full factorial: 9 indexes (`e<embedder>-c<chunk size>`) and 72 search setups (`e<embedder>-c<chunk size>-r<reranker>-h<hybrid>`) per dataset. Each setup runs once on its sealed index. Each index is built once (one-build-per-cell assumption, section 15).
- **Fixed in search.** Every setup saves its top 100 stored chunks in rank order, taken with that option on, so before OMRS context assembly merges neighbours (`top_k` 100, `fetch_k` 100, so the rerank pool is exactly 100 and the reranker returns all 100 in order). `similarity_threshold` 0.0. Metadata extraction `disabled`. All datasets go through the Markdown splitter and count tokens with the pinned Qwen3 tokenizer (revision `5cf2132a`). BioASQ and Legal passages are written as `.md`. Dense search is exact: no approximate vector index is built.
- **Answer stage.** 15 answer setups at the embedder and reranker size chosen on half A (section 14.1): 12 crossed setups (chunk size 3 x reranker on or off x hybrid on or off), each with 10 chunks of evidence; and 3 token-matched setups `c512-t20k`, `c1024-t20k`, `c2048-t20k` (reranker on, hybrid on), each with evidence cut at 20,480 real Qwen3 tokens. The `c2048` x 10 crossed cell keeps its 10 chunks. Each answer setup runs 3 times on all 1,160 questions.
- **Answer-stage order.** For each question: (1) search with the stored-chunk option on, at `top_k` 100; (2) take the head of the list: 10 stored chunks, or the stored chunks kept by the token cut; (3) run OMRS context assembly (overlap merge) on the kept whole chunks only, with no neighbour expansion; (4) add a truncated crossing chunk as its own evidence item, never merged; (5) call `Engine.answer` with these rows (`rows=`). The answer model sees the assembled evidence, as the product shows it. Each evidence item records the chunk IDs it holds. Collections follow the built-in `documents` profile, where `rows=` is allowed. The answer stage sends one search at a time, as the search stage does; only the paid answer calls run in parallel, up to `--answer-concurrency`. Why: parallel embed and rerank requests to llama.cpp need not give the same scores, and G1 compares these lists with the search-stage list.
- **Token cut.** The cut applies to stored chunks, before assembly. Stored chunks are taken in rank order and their own Qwen3 token counts are summed. A chunk is included when the total before it is below 20,480. The chunk that crosses the limit is truncated at the limit, and no later chunk is included. Truncation is recorded per question. When the top 100 stored chunks hold fewer than 20,480 tokens, the setup keeps all 100 and its evidence is shorter. Two token totals are recorded per question and setup: the cut total (the kept stored chunks, before assembly) and the realised evidence token total (the assembled evidence the model received). Assembly removes overlap text, so the realised total can be shorter than the cut total (section 22). The H8b reading in section 7 uses the cut total.
- **Other runs.** Two closed-book runs, one oracle run (section 13), and a length-controlled checker run (section 11.2).

## 6. Metrics

**Unit scoring.** Each setup's top 100 stored chunks (section 3) map to units (FinanceBench page, FreshStack document, BioASQ or Legal passage). The first occurrence of each unit is kept in rank order, and the list is cut at 10 units. On FinanceBench each stored chunk has exactly one page label, so a chunk covers its page. The PDF reader splits each filing page by page, so a FinanceBench chunk never crosses a page; a page caps chunk length, and the 1,024 and 2,048 levels can hold the same whole page. Section 21 reports the realised chunk lengths per level. On FinanceBench, the only dataset scored by page, a chunk with no page label maps to its own placeholder unit. On every dataset, a chunk that maps to no corpus unit (an unmapped chunk) maps to its own placeholder unit. A placeholder unit keeps its rank and is not relevant. These chunks are counted per setup and dataset. The FinanceBench seal refuses an index that holds any chunk with no page label (section 15). Relevance is binary. Every question has at least one gold unit.

For question q with gold set G_q (size R_q) and unit list L_q of up to 10 units, rel_i = 1 when unit i of L_q is in G_q (missing ranks count as 0). Following the trec_eval convention, every metric is a plain mean over the questions of a dataset:

- DCG@10 = sum over i = 1 to 10 of rel_i / log2(i + 1).
- IDCG@10 = sum over i = 1 to min(R_q, 10) of 1 / log2(i + 1).
- nDCG@10 = DCG@10 / IDCG@10. **Primary metric of the study.**
- Recall@10 = |L_q intersect G_q| / R_q.
- MRR@10 = 1 / (rank of the first gold unit in L_q), else 0.
- hit@page (FinanceBench) = 1 when any gold page is in L_q.
- **`evidence_recall_20k`** = share of G_q covered by the evidence taken from the top 100 stored chunks under the token cut of section 3. A stored chunk, whole or truncated, covers its one unit (on FinanceBench, its page). **Confirmatory endpoint for H6 and H7 on FinanceBench (rows 9 to 11).** `plan.json` flags both nDCG@10 and `evidence_recall_20k` as `primary`, because there the flag marks a metric that a primary hypothesis's decision rests on (the guide asks for a tolerance per primary metric); it does not mark a second headline metric.
- **alpha-nDCG@10** (FreshStack, secondary and descriptive): the nugget labels allow it (P3), so it is computed with the benchmark's own scorer, `alpha_ndcg` in `freshstack/retrieval/metrics.py` of `fresh-stack/freshstack` at commit `a1c8c45b` (SHA-256 `0f331649`), with `pyndeval` 0.0.8 at alpha 0.5 and depth 10. Nugget qrels are built as the official loader builds them. Each ranked unit list goes in with strictly falling scores, so the scorer cannot re-sort ties. The value per setup is the official mean over the setup's questions. It has no test, no Holm family and no decision. Full pin in `plan.json` `pins.scorers.freshstack_alpha_ndcg` (recorded 2026-11-26); the report step is `alphandcg35.py`.

**Answer metrics.** Per answer, then averaged over the 3 runs per question, then over questions.

- **Faithfulness of cited factual claims** (`faithfulness_glm_factual`): share of the answer's cited factual claims (classifier kinds fact and mixed) that GLM-5.3 calls supported. Refusal claims are reported apart. Claims and citations come from the answer itself: the answer model cites evidence by ordinal (for example `[1]`), the saved answer is split into claims, only prose segments with at least one valid ordinal go to the checker, and the checker sees one claim with the text of the evidence its ordinals cite (OpenSpec specs `grounded-answer-synthesis` and `benchmark-answer-scoring`). A prose segment with no valid ordinal (an uncited segment) is not a claim and is not checked, because it names no evidence to check against.
- **Uncited segments.** Co-outcome, reported per setup and dataset: `uncited_segment_share`, the share of the answer's prose segments that carry no valid ordinal. Registered sensitivity analysis: the classifier also sorts the uncited segments (it sees only the question and the segment, section 11.1); uncited segments it calls fact or mixed, or could not sort (section 12), count as unsupported, and faithfulness is computed again over cited and uncited factual segments together. Decided by the owner on 2026-11-14 (O7): the primary measure stays faithfulness of cited factual claims, and this version stays a sensitivity analysis only. Reason: OMRS answers are built to cite their evidence, so cited claims are the product's claims.
- **Correctness** (`ragas_answer_correctness`): Ragas 0.4.3 (Es et al. 2023) `AnswerCorrectness`, default weights (factual 0.75, similarity 0.25), judge `openai/gpt-oss-120b`, local 4B embedder. The judge sees the question, the answer and the reference answer, never the contexts. FreshStack's reference is `answer_text` (the accepted Stack Overflow answer).
- **Secondary**: Clef-Flash faithfulness, FinanceBench number match (`protocol.md` section 0.6 rule), refusal rate, the four other Ragas metrics, closed-book and oracle correctness.
- **FinanceBench number match, counting.** Every number in the reference must match a number in the answer. A year written alone (for example 2019) is a number like any other. A number joined on its left to a letter, digit, point or comma is not read as a number, in the reference or the answer, and a hyphen between two numbers is not a minus sign. One exception: a whole-word fiscal-year label `FY` followed by exactly four digits reads as that year (`FY2019` is 2019; `FY19` and `XFY2019` are not read). A number joined on its right to a letter that is no scale word or percent sign is not read either (`777X`, `1x`). A one-letter scale (`m`, `b` or `k`) counts only when the number has a currency sign (`$3M` is 3,000,000). Without a currency sign, a number joined to that letter is not read (`3M`, the company), and a number with a space before it reads without the scale (`2 b` is 2). Spelt-out and two-letter scales (`million`, `mn`, `bn`) always count. A question whose reference holds no number is not scored: it leaves the number-match denominator, and the report states the denominator per setup (24 of the 150 references hold no number under these rules). An answer still missing scores 0 (section 12) on a scored question only. Scores are averaged over the 3 runs, then over the scored questions.
- **Refusal rate.** Per answer setup and dataset: refusal claims divided by all claims, pooled over questions and the 3 runs. An unclassified claim stays in the denominator as not refusal (section 12). Its 95% interval, and that of each checker's unsupported rate on refusal claims, is a percentile bootstrap by question (10,000 resamples, section 11.2 percentile rule), because claims of one question are not independent. The descriptive faithfulness intervals of the refusal report use the same bootstrap. Both use seed 20261136.

## 7. Hypotheses

Each null is a zero effect. Every test is two-sided. A directional contrast counts when its Holm-adjusted p is below 0.05 and its estimate has the predicted sign (this is a one-sided test at 0.025). A two-sided contrast counts when its Holm-adjusted p is below 0.05. A two-sided hypothesis needs the same sign. Under a both-datasets rule (H6, H8a, H8b), the row must count with the same sign on FinanceBench and on FreshStack; if it counts with opposite signs, it is reported as a dataset-dependent effect, and the hypothesis does not hold. Under a 2-of-3 rule (C1 and C2 in section 18), the row must count with the same sign on at least 2 of the 3 core datasets. A count with the opposite sign on the third dataset is reported as a dataset-dependent effect and does not stop the hypothesis holding. The report always states the direction. Marginal contrasts weight every cell of the other factors equally (for example, the embedder effect averages over 24 cells, 18 of them reranker-on). Row numbers refer to section 8.

- **H1 (embedder).** Within scope S, a bigger embedder ranks gold units higher. Rows 1 (4B minus 0.6B) and 2 (8B minus 4B), nDCG@10, directional. Null: each contrast is zero. Holds: each step holds when its row counts on at least 2 of the 3 core datasets. H1 holds in full when both steps hold, in part when one does.
- **H2 (reranker).** Within scope S, the reranker raises nDCG@10. Row 3 (mean of the three reranker sizes minus off), directional. Null: zero. Holds when row 3 counts on at least 2 of 3 core datasets.
- **H3 (hybrid).** Within scope S, hybrid search raises nDCG@10. Row 4, directional. Null: zero. Holds as H2.
- **H4 (combining reranker and hybrid: simple effects).** Within scope S, reranker plus hybrid beats each alone. Row 5 (both on minus reranker only) and row 6 (both on minus hybrid only), directional. These are simple effects, not an interaction test; the interaction is reported descriptively with its interval. Null: each contrast is zero. Holds on a dataset when both rows count there; holds overall on at least 2 of 3 core datasets.
- **H5 (reranker size).** Within scope S, a bigger reranker ranks better (reranker-on setups). Rows 7 (4B minus 0.6B) and 8 (8B minus 4B), directional. Holds as H1.
- **H6 (chunk size, search).** Within scope S, chunk size changes retrieval. Rows 9 (1,024 minus 512) and 10 (2,048 minus 1,024), two-sided. Endpoint: `evidence_recall_20k` on FinanceBench, nDCG@10 on FreshStack. Null: each contrast is zero. Holds when the same row (9 or 10) counts with the same sign on FinanceBench and on FreshStack. BioASQ is a sanity check (most passages are shorter than 512 tokens, so chunk size barely changes its chunks); Legal is exploratory. FinanceBench sensitivity: nDCG@10 (a chunk covers its page); the report gives sign agreement per row with the endpoint.
- **H7 (embedder by chunk size).** Within scope S, a bigger embedder gains more from bigger chunks. Row 11: (8B at 2,048 minus 8B at 512) minus (0.6B at 2,048 minus 0.6B at 512), marginal over reranker and hybrid, directional, with the H6 endpoints. It is a difference of differences with coefficients +1, -1, -1, +1 on these four cells (section 9 point 1). Null: zero. Holds when row 11 counts on both FinanceBench and FreshStack. BioASQ is a sanity check, Legal exploratory. Expected to have a wide interval (section 10).
- **H8a (chunk size with context length, answers).** Within scope S, chunk size changes faithfulness and correctness in the 12 crossed setups, where context length grows with chunk size (long contexts can hide evidence: Liu et al. 2024). Rows 12 to 13 (faithfulness) and 14 to 15 (correctness): 1,024 minus 512 and 2,048 minus 1,024, marginal over reranker and hybrid, two-sided. Expected direction for faithfulness: falls as chunks grow (Wang et al. 2024); the report gives the sign. Null: each contrast is zero. Per outcome, holds when the same row counts with the same sign on FinanceBench and on FreshStack. Legal is exploratory. BioASQ chunks barely change with chunk size, so BioASQ rows 12 to 19 are sanity checks, like rows 9 to 11 (section 8).
- **H8b (chunk size at a fixed pre-assembly evidence budget, answers).** Within scope S, chunk size changes faithfulness and correctness when the evidence is cut to the same budget of 20,480 tokens of stored chunks, before assembly (the cut total, section 3). Rows 16 to 17 (faithfulness) and 18 to 19 (correctness): `c1024-t20k` minus `c512-t20k` and `c2048-t20k` minus `c1024-t20k`, two-sided, at reranker on and hybrid on with the chosen sizes (so H8b is conditional on that cell). Holds as H8a (per outcome, the same row counts with the same sign on FinanceBench and on FreshStack). **Reading fixed now:** H8b fixes the pre-assembly budget, not the evidence the model sees. Assembly removes overlap text, and the amount removed can differ between setups, so H8b does not separate chunk size from context length. When H8b holds for outcome X and a registered sensitivity analysis agrees, the claim is "chunk size changes X at a fixed pre-assembly evidence budget". Every question stays in H8b. The sensitivity analysis repeats the H8b row on the questions where all three `-t20k` setups reach a cut total (section 3) of at least 95% of 20,480 tokens (19,456). The cut total of a question and `-t20k` setup is the one any answer run of that setup saved; all runs share it, because it comes from the one search list (G1). A question with no saved cut total in some `-t20k` setup (every run of it missing) leaves this sensitivity analysis and is counted (`no_cut_total`). The sensitivity analysis agrees when that row's estimate has the sign of the row's H8b result on FinanceBench and on FreshStack. A sign reversed on either dataset, or on both, is disagreement. The report gives the questions it keeps per dataset. Beside each H8b result it gives the realised (assembled) token total per setup, so a reader can see how far assembly changed the amounts. When H8a holds and H8b does not, the claim is "chunk size together with context length changes X".

**Error rates of the composite rule.** Holm within each dataset plus "at least 2 of 3 datasets" (H1 to H5) or "FinanceBench and FreshStack" (H6 to H8b) is conservative. Under the null on three independent datasets, a false "holds" for one directional contrast has probability about 3 x 0.025 squared, about 0.002, before Holm. Under the FinanceBench-and-FreshStack rule it is about 0.025 squared (about 0.0006) for a directional row, and 2 x 0.025 squared (about 0.001) for a two-sided row under the same-sign rule. Power falls the other way: at a per-dataset power of 0.6, the 2-of-3 rule has about 0.65; at 0.5, about 0.50.

## 9. Analysis model

One clustered method gives every estimate, interval and p-value. There is no mixed model.

1. **Per-question contrast score.** For row k and question q, d_qk is the mean of question q's scores over the cells at the first level minus the mean over the cells at the second level (equal cell weights). Answer scores are first averaged over the 3 runs. This recipe does not apply to row 11. For row 11, each of the four H7 corner cells is first averaged over reranker and hybrid, and d_q11 = (+1) e8b-c2048 (-1) e8b-c512 (-1) e0.6b-c2048 (+1) e0.6b-c512. Example: scores 0.8, 0.2, 0.3 and 0.7 for these cells in this order give d = 1.0; the general recipe would give 0.5. The known-answer fixture (RDY task 15.6) holds this case.
2. **Estimate.** The plain mean of d_qk over the questions that enter the row (section 12).
3. **FreshStack, BioASQ and Legal.** The decision test is defined by its closed form. Let n be the number of questions that enter the row and r_q = d_qk minus the estimate. Estimate: the mean of d_qk. Variance: (sum of r_q squared) x (n / (n minus 1)) squared / n squared. Reference distribution: t on n minus 1 degrees of freedom, for the p-value and the 95% interval. This is the Mancl and DeRouen (2001) bias-reduced sandwich for an intercept-only model with one row per cluster. It equals the paired t-test variance times n / (n minus 1), so it needs no convergence fallback. With complete data the estimate equals the cell-means contrast of the full-factorial model. **Implementation:** `statsmodels` GEE (Liang and Zeger 1986) of d_qk on an intercept (Gaussian family, identity link, independence working correlation, clusters = questions, `cov_type="bias_reduced"`) gives the estimate and the variance. The p-value and the interval are always computed from the t reference above, whatever reference the library reports by default. A known-answer test (RDY task 15.6) checks that the library estimate and variance equal the closed form. If they do not, the closed form is used and the difference is reported. The closed form was checked against `statsmodels` 0.15.0 on 2026-11-14 on a seeded fixture of 30 questions: the GEE estimate and variance matched it to 1e-10. The library reports a normal reference for the p-value (`use_t=False`), so the code takes the t reference itself. The build-time test of RDY task 15.6 stays.
4. **FinanceBench (questions share documents).** The decision p-value comes from a document-level sign-flip permutation test. The statistic is the question-weighted mean of d_qk. Under the null, the sign of each document's sum of d_qk is flipped at random: 100,000 draws, seed 20261101, p = (1 + number of draws with an absolute statistic at least as large) / 100,001. "At least as large" uses a tie tolerance of 1e-12 (a draw counts when its absolute statistic is at least the observed one minus 1e-12); this tolerance is part of the registered test. The 95% interval inverts the same test on the same 100,000 draws: its ends are the lowest and the highest shift not rejected at 0.05, and each end is found by bisection to 0.0001. The draws are one matrix, `numpy.random.default_rng(20261101).integers(0, 2, size=(100000, n_documents))` with the default integer type (no `dtype` argument; another integer type draws another stream). Each 0 maps to minus 1 and each 1 to plus 1, with one row per draw and one column per document in sorted document-ID order. Known-answer check: with `size=(4, 6)` the first row is 1, 1, 1, 0, 0, 0 before the mapping. The document of each question comes from the gold table through the search score records, never from an answer row, so a closed-missing answer keeps its question's document. The test assumes each document's sum is symmetric about zero under the null. The interval also assumes a constant additive shift for every question (a location-shift model); the point estimate and the p-value do not need it.
5. **Decision.** A row whose estimate is zero and whose variance is zero gets p = 1. Any NaN p-value stops the analysis with an error before Holm runs. Holm (alpha 0.05) within each family (Carterette 2012) on the decision p-values, then the sign rule of section 7, then the 2-of-3 or both-datasets rule of each hypothesis (with the same-sign rule of section 7 for two-sided rows).
6. **Sensitivity checks, registered, never decisive.** FreshStack and BioASQ: paired permutation test by question (10,000 shuffles, seed 20261101; Smucker, Allan and Carterette 2007; Urbano, Lima and Hanjalic 2019). FinanceBench: the GEE of point 3 with document clusters, with the t reference on the number of documents minus 1 degrees of freedom. The permutation test takes the questions in `qid` order sorted as text and uses Python `random.Random(20261101)`: in each shuffle, each question's d keeps its sign when the next `random()` value is below 0.5, else the sign flips. Its statistic is the absolute sum of d, its tie tolerance is 1e-12, and an observed sum of zero gives p = 1. Sensitivity p-values get Holm within the same family as the decision p-values (gated rows at p = 1), so "counts" means the same for both. The report shows each sensitivity p-value unadjusted and Holm-adjusted. Every row where the decision and the sensitivity check disagree on "counts" is listed in one table. No confirmatory claim rests on a sensitivity check.
7. **Pooled H8 estimate (A18, secondary, decides nothing).** For rows 12 to 19, one inverse-variance-weighted mean of the FinanceBench and FreshStack estimates: weight = 1 / variance, where the variance is the GEE bias-reduced variance of point 3 (FinanceBench: the document-cluster GEE of point 6). 95% interval on a normal reference. It is always printed beside both per-dataset estimates. When the two estimates have opposite signs, the pooled row is marked "signs differ". Its interval is read against no SESOI (section 10: only nDCG@10 has one). It changes no verdict: H8a and H8b keep the both-datasets rule. Rows 9 to 11 are not pooled (FinanceBench uses `evidence_recall_20k`). It is a fixed-effect weighted average of these two datasets, not a population effect. A row not testable on at least one of the two datasets, or with zero estimate variance on either, is not pooled.
8. **Search-stage scores** come from one run per setup. **Intervals** printed beside Holm decisions are unadjusted 95% intervals (Miller 2024).

A non-significant result means no difference was detected at this sample size. The study makes no equivalence claim and runs no TOST. Section 10 reads each interval against plus and minus 0.02; that reading is descriptive and adds no test.

## 10. Smallest effect of interest and precision

- **Smallest effect of interest (SESOI).** 0.02 nDCG@10, decided by the owner on 2026-11-14 (O2). The concept follows Lakens 2017. It changes no decision: every hypothesis is tested against zero, and each row's interval is read against plus and minus 0.02. No other endpoint has a SESOI; their intervals are reported without one.
- **Why 0.02.** No IR standard fixes this value; it is the authors' justified choice. (1) User terms: for a question with one gold unit, moving it from rank 2 to rank 1 raises nDCG@10 by 1 minus 1/log2(3), about 0.369. A mean gain of 0.02 is about one question in 18 with its gold unit moved from second to first place (0.02 / 0.369 = 0.054); 0.01 is about one in 37, and 0.05 about one in 7. Bringing a gold unit from outside the top 10 to rank 10 adds 1/log2(11), about 0.289, so 0.02 is about one question in 14. (2) Lower bound from the design: selection treats setups within 0.01 as tied (section 14.1) and the tolerance on another back end is 0.005 (section 15), so the SESOI must be above 0.01. (3) Cost: each factor step costs something real. A 4B to 8B model roughly doubles memory, a reranker scores 100 more pairs per query, and hybrid search adds an index. The authors judge that a gain which changes the top result for fewer than about one question in 20 does not pay for such a step for an OMRS user. (4) Published effects (Zhang et al. 2025; MTEB retrieval scores are nDCG@10 x 100): on MTEB(eng, v2) retrieval the 0.6B, 4B and 8B embedders score 61.83, 68.46 and 69.44 (steps about 0.066 and 0.010). On MTEB-R, from a 61.82 first stage, the 0.6B, 4B and 8B rerankers score 65.80, 69.76 and 69.02 (gains about 0.040, 0.079 and 0.072; size steps 0.040 and minus 0.007). These effects span about 0.01 to 0.08 in size, and 0.02 separates the two smallest steps from the rest. (5) Not set by power: the datasets are fixed, so the study chooses no sample size, and 0.02 was not chosen to match what the design can detect. The sensitivity power analysis below (A17) gives the smallest effect each test detects with power 0.80 (the MDE). On FreshStack and FinanceBench the MDE is about 0.04 to 0.08, so a true effect of 0.02 is not reliably detected there. On BioASQ it is about 0.02 to 0.03. A row whose interval cannot exclude 0.02 is reported as "cannot rule out a small effect". (6) Sensitivity: the report also reads every interval against 0.01 and 0.05.
- **Precision (owner decision, 2026-11-26).** This study has no a priori power analysis, no pilot and no observed power. It reports one sensitivity power analysis (A17, below). Precision is reported through each row's 95% confidence interval. Amended 2026-11-26 (pre-freeze, owner; `plan.json` amendment A16): each interval is read against the SESOI of 0.02 nDCG@10 in four cases:
  1. The interval is fully inside -0.02 to +0.02: no meaningful difference.
  2. The interval is fully above +0.02, or fully below -0.02: a meaningful difference.
  3. The interval excludes zero but crosses +0.02 or -0.02: a real difference that can be too small to matter.
  4. The interval includes zero and crosses +0.02 or -0.02: the test cannot tell.

  The reading is descriptive only: it adds no test and no p-value. The hypothesis verdicts stay the Holm-corrected tests.
- **Sensitivity power analysis (A17, owner decision, 2026-11-26).** The datasets are fixed, so the study chooses no sample size. The analysis asks which effect each test would detect 80% of the time with the questions it has (Lakens 2022; Webber, Moffat and Zobel 2008; Sakai 2016). The table gives an approximate value of that smallest effect, the MDE.
  - Formula: MDE = (z at 1 minus alpha/2, plus z at 0.80) x SD / square root of n. Power is 0.80. Tests are two-sided. Alpha is 0.05 divided by the Holm family size: 19 on FinanceBench, 19 on FreshStack and 8 on BioASQ. The question counts are n = 150, 203 and 707. `mde35.py` computes it (`assumed_table` and `mde_row`). It runs once, before the freeze, on no main-run score. Cost: $0. No pilot runs.
  - Why alpha is 0.05 divided by the family size: it is the first and strictest Holm step. Later Holm steps use a larger alpha, so they detect smaller effects than the table shows. The table is conservative here too.
  - The formula is a normal approximation for a paired test on per-question differences. The registered tests differ: FreshStack and BioASQ use a GEE with a bias-reduced variance and a t reference (section 9), and FinanceBench uses a document-level sign-flip test (section 9). A directional row also needs the predicted sign (section 7). So the table approximates the sensitivity of those tests. It is not their exact power.
  - SD source: the registered assumed range 0.15 to 0.25 (`mde35.ASSUMED_SD`) for every row. Why this range: it was set on 2026-11-16 (`mde35.py`, commit 4de9f2f4), before any SD below was computed. The three measured stand-in SDs (0.113, 0.167 and 0.180) fall in or near it. The one below it (0.113, row 8) gives a smaller MDE (0.031) than the range does, so the table overstates the MDE for that row. That is the conservative direction.
  - FinanceBench design effect: the 150 questions share 84 filings. The design effect of that grouping is not measured before the freeze, so n is not divided, as `assumed_table` does. For the same SD, a design effect above 1 raises the FinanceBench MDE (`mde35.py` floors the design effect at 1). The table is not updated after the run.
  - Rows 9 to 11 on FinanceBench use `evidence_recall_20k`. The same arithmetic and the same SD range apply to them. Row 11 is a difference of differences. The table does not model that scale, so the MDE of row 11 is not known. A16 already expects a wide interval for it.
  - The table covers retrieval rows 1 to 11. Answer rows 12 to 19 have no registered SD before the freeze, so the table gives no MDE for them.

### 11.2 Gates

Gate decisions are computed and recorded, with a time, before any H8 contrast result is computed.

**Interval method for every gate.** Every gate interval (kappa, the AUC lower bound, the specificity difference) is a percentile bootstrap: 10,000 resamples, resampling by question, so all claims or answers of one question move together. Each interval has its own seed (section 16). Percentile rule: order statistics with no interpolation, as in `experiments/_lib/stats_d6.py` `paired_bootstrap`. The resampled statistics are sorted in ascending order; the lower bound is the value at zero-based index int(0.025 x n) and the upper bound the value at zero-based index int(0.975 x n) minus 1, where n is the number of resampled values the interval uses. For n = 10,000 these are indexes 250 and 9,749 (the 251st and the 9,750th smallest values). The rule applies after the fail-closed substitution below.

**Undefined statistics fail closed.** A statistic is undefined when its sample lacks a class it needs: kappa when both label sets hold one and the same class (chance agreement 1); AUC when the human labels hold one class; the specificity difference when a chunk-size level holds no human-supported claim. The rule:

1. Undefined on the full labelled sample: the gate fails. For the differential-error rule, rows 12, 13, 16 and 17 become not testable.
2. Points 2 to 4 apply to every undefined resample, also when the full sample is defined. A resample is never drawn again. Each undefined resample is counted once, whichever chunk-size level or class it lacks, and the report gives the count.
3. More than 5% of resamples undefined (over 500 of 10,000): the gate fails as in point 1.
4. Otherwise an undefined kappa resample takes 0 and an undefined AUC resample takes 0.5 (the chance values). Both sit below their pass thresholds, so they can never help a gate pass. An undefined specificity-difference resample has no chance value, so it is left out of the interval; point 3 caps this at 5%.

Why: a chance value makes an undefined resample count against a pass, and point 3 stops a sample with too few items of one class from passing on its defined resamples alone. A bootstrap stratified by label would keep both classes in every resample, but the resampling unit is the question, and label and chunk size are not question properties.

- **Faithfulness gate, per checker.** Cohen's kappa (Sim and Wright 2005) of the checker against the human label: point estimate at least 0.60 and lower 95% bound at least 0.40. Prevalence, raw agreement and PABAK are reported beside kappa. Sample: 450 claims from the crossed setups, 150 per chunk size, 50 per core dataset within each chunk size, at most one claim per answer, seed 20261116. The claims are drawn from answers to all questions (both halves), because H8a and H8b are tested on all questions. This sample is drawn only after gate 3 reports; no answer or scoring stage waits for it. If gate 3 fails, the pool is all cited claims (no kind filter). Draw procedure: the pool holds the cited claims of every crossed answer, all 3 runs, whose saved kind is fact or mixed, or that the classifier left unclassified (section 12 treats those as factual). Refusal claims are not in the pool, because the primary measure leaves them out (section 6). An answer is one (setup, run, question). Within each cell of chunk size and core dataset, in sorted order, the pool is sorted by item ID and shuffled with one `random.Random(20261116)` generator; the first 50 claims from distinct answers are kept. The 450 claims are then shuffled with the same generator. The correctness sample below stays on half B. The gate is pooled over the three core datasets because 150 claims per dataset are too few for a per-dataset gate; kappa per checker and per core dataset is reported with its interval as descriptive and decides nothing. "Can't tell" counts as not supported (the binary benchmark scale); kappa is also reported with "can't tell" items left out. If GLM-5.3 fails, rows 12, 13, 16 and 17 are not testable on every dataset.
- **Differential-error rule.** "Unsupported" is the positive class. Specificity is the share of human-supported claims the checker calls supported. The rule uses GLM-5.3, the main checker; Clef-Flash specificity is reported only. If the 95% interval of the GLM-5.3 specificity difference (2,048 minus 512), or of the GLM-5.3 sensitivity difference (2,048 minus 512), excludes zero in either direction (the same 95% interval rule for both, computed on one set of resamples by question, seed 20261126; the rule fires if either interval excludes zero; the undefined-statistic rules apply to sensitivity as to specificity, with a level holding no human-unsupported claim counted as undefined), H8a and H8b faithfulness (rows 12, 13, 16, 17) is exploratory and not testable. Sensitivity per chunk size is reported.
- **Correctness gate, per core dataset.** 50 questions per core dataset drawn from half B (seed 20261113); for each question, one answer from run 1 of an answer setup chosen uniformly at random by the same seed. 50 Legal answers, drawn the same way, are also labelled and reported without a gate. If drop step 1 (section 17) removes Legal answer generation, the Legal answers are not drawn: the sample is 150 answers and every label total falls by 50 (section 11.3). Legal has no gate, so no confirmatory row changes. The Ragas score is cut at 0.5 (fixed before labelling). The human label for this gate is the agreed L1 and L2 label (section 11.3). The gate passes on a dataset when kappa is at least 0.60 with a lower 95% bound of at least 0.40, computed with "can't tell" items scored both as correct and as not correct (both must pass). The continuous score is validated too: its AUC against the human label must have a lower 95% bound above 0.5, computed with "can't tell" scored both as correct and as not correct (both must pass). If the gate fails on a dataset, rows 14, 15, 18 and 19 are not testable there. Prevalence, raw agreement and PABAK are reported beside kappa (Feinstein and Cicchetti 1990; Byrt, Bishop and Carlin 1993).
- **Length-controlled check (registered sensitivity, no gate).** 300 claims from `c2048` crossed answers (seed 20261119). The frame is the cited claims whose saved kind is not refusal, from the `c2048` crossed answers of every dataset with answers, Legal RAG Bench included unless drop step 1 removed its answers. GLM-5.3 and Clef-Flash judge each claim again against one 512-token window of each cited chunk: the chunk is split into consecutive 512-token windows, and the window that shares the most distinct lower-case claim words is kept (ties go to the earlier window). The report gives the verdict change rate with a Wilson interval. This sample is drawn only after gate 3 reports; no answer or scoring stage waits for it. If gate 3 fails, the pool is all cited claims (no kind filter).

## 12. Missing outcomes

Every question stays in its dataset's denominator. Every exclusion is counted per setup and row and printed.

- **Resend rule.** "No result saved" means that no answer text, verdict or score was saved for the call. An error row with no content is not a result, with one exception: an empty reply from the answer model (OMRS reports it as the error `EMPTY_REPLY_ERROR` with no text) is a returned empty answer. It is saved as an answer with empty text, is final and is never resent. Failed answer calls, failed search rows, failed local-checker calls and failed Ragas metrics stay pending and are resent on `--resume`. A Ragas row keeps an `unjudged` list of its failed metrics, and `--resume` runs only those metrics again. A checker call that returns with an error has failed; it is never a verdict. Any returned content is final, including a refusal or an empty answer. A resend never depends on content. **Cap:** only a send that returns an error that is not a rate limit and not out-of-credit counts toward the cap. A call that has returned such an error 3 times (the first send plus 2 resends, across resumes) is closed as missing and follows the rule for its kind below; the stage records it and continues. Not counted toward the cap: the rate-limit gate (its attempt count is recorded at the freeze; default 6), the short retry on a 402 response, the `out_of_credit` stop, and a call cut off before its result was saved (it is resent on resume). The checker cap counts per claim call: each claim verdict and each claim error is saved per claim, `--resume` sends only claims with no verdict, and a third error closes that claim only. An answer with a closed claim keeps its other verdicts but is an unjudged row for faithfulness (below). A Ragas metric that returns NaN, or returns no number, has returned content: the score is final, saved as `null` with `not_defined`, never resent and never counted toward the cap. `resent_calls` counts every harness-level resend, per setup and role; for the checker it counts resent claim calls. The answer stage writes its dispatch record just before the paid answer call, so a failed search or a local error before that call is not a resend. Transport retries inside the client libraries, bounded by the pinned library defaults, are not counted in `resent_calls` (section 22). Cost comes from provider billing, so these retries do not lower the reported cost.
- **Search.** A list shorter than 10 units scores its missing ranks as not relevant. A search row still missing after `--resume` scores 0 and is listed. A reranker call has failed when it gets an HTTP error, gets no reply within 600 s, or gets a bad reply (a score outside 0 to 1, or an index not scored exactly once). A failed reranker call saves no row: the stage stops, and `--resume` sends the query again. Un-reranked rows are never scored as a reranker-on result.
- **Failed answer call.** The resend rule above applies: a call is resent only when no result was saved, never because of content, and each resend is counted (`resent_calls`). An answer still missing when the run closes scores 0 for correctness and number match, and counts as an answer with no factual claim. It has no answer text, so it is not sent to the Ragas judge or to a checker. Its correctness 0 is a scored value, so the unjudged-row rule below does not apply to it, and it stays in the correctness complete cases.
- **Answer with no factual claim.** Faithfulness is undefined for that run. Per question and setup, faithfulness is the mean over the runs that have at least one factual claim. A question enters a faithfulness row only when every cell used by that row has a value (complete cases). Two registered sensitivity analyses keep every question: no-claim answers scored 1, and scored 0. The refusal rate per setup is reported as a co-outcome.
- **Unjudged rows.** This rule applies only to an answer that exists and whose Ragas or checker call was closed missing. Ragas and checker rows that failed are retried on `--resume`. A row still unjudged when the run closes leaves that row's complete cases and is counted; a sensitivity analysis scores it 0.
- **Unclassified claims.** A claim the classifier still fails on after `--resume` is treated as a factual claim: it stays in the faithfulness denominator and is counted. A sensitivity analysis leaves such claims out.
- **Unclassified uncited segments.** The same rule applies to an uncited segment. In the uncited-segment sensitivity analysis (section 6), a segment the classifier still fails on after `--resume` counts as factual, so it counts as unsupported. It is counted.
- **How each kind of row enters the answer outcomes.** A cell is one question and answer setup; its value is the mean over its runs.
  - *Missing answer* (closed missing, no text) and *empty answer* (returned with no text): correctness 0 and number match 0 (on a scored question), both in the complete cases. For faithfulness the run is a no-claim run. Neither is unjudged. A checker does not judge either, and the Ragas score of an empty answer is not used.
  - *No-claim run*: no faithfulness value; the cell is the mean of the other runs (rule above).
  - *Unjudged run* (an existing answer whose checker row, or one of its claims, or whose Ragas correctness metric was closed missing): the whole cell has no value for that outcome, and the other runs do not stand in for it. The question leaves that row's complete cases and is counted. A sensitivity analysis scores the run 0.
  - *Not-defined run* (Ragas correctness NaN or no number): the run has no correctness value, and the cell is the mean of the other runs. A sensitivity analysis scores the run 0, like an unjudged run. Why: a not-defined score is returned content, but a judge-side cause cannot be ruled out, so the primary result must be shown not to depend on leaving it out.
  - *Unparseable verdict*: returned content, so it counts as not supported, in the confirmatory join and in the refusal report alike.
  - *Counts.* Each contrast row reports `excluded` against every question of its dataset, so a question with no value in any cell counts too. `excluded` splits into `excluded_unjudged` (a used cell has an unjudged run), `excluded_not_defined` (otherwise, a used cell has a not-defined run) and `excluded_no_value` (the rest). The join counts unjudged runs per dataset, setup and outcome (`unjudged`), not-defined runs per dataset and setup (`not_defined`) and unparseable verdicts per setup (`unparseable_verdicts`). The closed-book cross-table gives `misses_total`, `no_rag_score` and `no_closed_book_score` per setup.
- **Part 2 rules** are in section 18.

## 13. Floor, ceiling and closed-book runs

All are single runs on all 1,160 questions, scored like the main runs, descriptive only, with no hypothesis test. The report says that the main setups average 3 runs and these do not.

- **Closed-book, own-knowledge prompt (floor).** The answer model with no evidence and a fixed prompt that asks for an answer from its own knowledge. The prompt text is `OWN_PROMPT` in `closedbook35.py`, shown here as a Python string; `{query}` is replaced by the question text (section 4 query rule):

  ```python
  "Answer the question from your own knowledge. Be concise and give the answer directly.\nQuestion: {query}\nAnswer: "
  ```

  Its SHA-256 is pinned with the other prompt hashes (section 16, P13).
- **Closed-book, RAG prompt.** The main answer prompt with an empty evidence block, so it differs from the RAG setups only in the evidence. A registered sensitivity analysis.
- **How the closed-book prompts are sent.** Each closed-book prompt is sent as one direct completion call to OMRS's answer model, with the frozen answer settings (model, host, reasoning, output cap, temperature and seed). The RAG prompt cannot go through `Engine.answer`: the OMRS answer path never calls the model on empty evidence. The test pod checks that this direct call carries the frozen answer settings (RDY task 9.2).
- **Oracle (ceiling).** Gold units given directly as evidence (Legal gold passage, FinanceBench gold page texts, BioASQ gold passages, FreshStack gold documents), capped at 20,480 Qwen3 tokens with truncation recorded. It has no distractors, so it is an upper bound, not a fair comparison.
- **Contamination sensitivity.** Rows 14, 15, 18 and 19 are re-run on the questions that both closed-book runs answer wrongly (Ragas correctness below 0.5). If the drop order of section 17 drops the RAG-prompt run, the subset uses the own-knowledge run alone, and the report says so. The report gives closed-book correctness per dataset beside every correctness table, and a per-question cross-table on retrieval misses (closed-book correct or not against RAG correct or not).
- **Retrieval miss.** A question that has no gold unit among the units of the evidence the answer model saw for that answer setup. For a 10-chunk setup, these are the units of the 10 head stored chunks. For a `-t20k` setup, they are the units of the token cut, so a miss is `evidence_recall_20k` of 0. The units come from the single search-stage run of the matching search setup (G1 makes the answer runs equal to it). `recall_at_10` of 0 is not used: its 10 units can come from stored chunks below rank 10, which the answer model of a 10-chunk setup never saw.

## 14. Selection rule, order of work and RQ1 headline

### 14.1 Selection (A3), half A only

Pooled score = plain mean of the per-dataset mean nDCG@10 over FinanceBench, FreshStack and BioASQ, on half A. Legal takes no part.

1. **Embedder.** Pooled score per embedder averaged over all other factors. Choose the smallest embedder within 0.01 of the best. "Within 0.01" means a gap of at most 0.01 + 1e-9 on the unrounded pooled scores, here and in steps 2 and 3, so a gap of exactly 0.01 counts as within.
2. **Reranker size.** At the chosen embedder, reranker-on setups averaged over chunk size and hybrid. Choose the smallest size within 0.01 of the best. Equal scores go to the smaller size.
3. **A3 cell (for RQ1 and Part 2).** At the chosen embedder and reranker size, the 12 cells (chunk size x reranker on or off x hybrid on or off). A cell ties the best cell when its pooled score is within 0.01 of it. Among tied cells choose, in order: (1) reranker off, (2) hybrid off, (3) the chunk size with the lowest index cost, (4) the smaller chunk size. Each step applies to the cells left by the step before.

- **Index cost** = stored vector values: number of chunks times embedding dimension, summed over the three core datasets. It is known from the sealed indexes before any score.
- **Configuration hash** = SHA-256 of the canonical JSON (keys sorted, no spaces, UTF-8) of the selected cell's resolved settings, with the SHA-256 of `halves.json` as one top-level field named `halves_sha256`. The JSON is written with no ASCII escaping. `selection.json` holds the same `halves_sha256` and the `configuration_hash`.
- `selection.json` records every pooled score, both chosen sizes, the A3 cell and the hash.

### 14.2 Order of work

1. Build and seal the 9 indexes; G2 passes before any search writes into the shared output folder.
2. Run the 72 search setups on all questions. The search stage saves ranked lists and timings only. For each ranked stored chunk it saves the chunk ID, score, file stem, page label and token count from the pinned Qwen3 tokenizer. It saves no chunk text. The scorer computes `evidence_recall_20k` from these saved counts. A truncated crossing chunk still covers its unit (section 6), so the cut needs the counts only. It reads no gold label and computes no metric, and its summaries hold counts and timings only.
3. Score half A only. A separate scorer runs per half; its guard refuses to score half B before step 4. Apply 14.1. Write `<out>/selection.json`, where `<out>` is the run output folder.
4. Time-stamp the configuration hash with a file upload to the registered OSF project (O1, decided by the owner on 2026-11-14). Record the upload in `<out>/osf-timestamp.json` with three fields: `uploaded_at` (the upload time), `file_sha256` (the SHA-256 of the uploaded file) and `configuration_hash`.
5. Only then score half B, and start the replicate pods (answer stage).

**Half-B guard.** Every half-B score write goes through one guard. It opens only when `<out>/selection.json` and `<out>/osf-timestamp.json` both exist, the record sets all three fields, and its `configuration_hash` equals the one in `selection.json`. Otherwise it refuses and names the missing file, the missing field or both hashes. Half-A scoring needs neither file. The main join writes `answer-scores.jsonl`, which holds half-B rows, through this guard. It runs after step 5, so the time-stamp exists. No join runs before the time-stamp: step 3 reads the half-A score files of the scorer, not the join. A smoke join writes no `answer-scores.jsonl`. The main join calls the guard before it reads or writes anything, so a locked half B leaves no `join.json`. The confirmatory analysis, the closed-book cross-table and the refusal report also call the guard before they read or write. A smoke join skips the guard.

The word "sealed" applies to indexes only. Half B is held out from every selection step; its search lists exist on disk before step 4, but no half-B score is computed before it.

### 14.3 RQ1 headline

- **Retrieval headline**: the A3 cell's nDCG@10 on half B, per core dataset, with its 95% interval. The 72-setup table on all questions is descriptive.
- **Answer headline**: the answer setup that matches the A3 cell, on half B, faithfulness and correctness per dataset with intervals.
- **Search-cost figure**: the expected maximum of the pooled half-A score over n setups drawn at random, adapted from Dodge et al. 2019 (drawn without replacement), computed exactly from the scores sorted in ascending order, v(1) to v(N), as the sum over i = n to N of v(i) x C(i minus 1, n minus 1) / C(N, n). One curve over the 12 A3 cells (n = 1 to 12) and one over the 72 setups (n = 1 to 72). RAGFlow has no point unless its matched search runs (section 18); then RAGFlow gets its own curve over its half-A cells.

## 17. Budget, ceiling, stop rule and drop order

- **Estimate (amended 2026-11-25, pre-freeze, owner approval).** **$1,122**: RunPod GPU (RTX 4090) $410; OpenRouter answers (DeepSeek V4.1 Flash) $180; OpenRouter Ragas judge and claim sorter (gpt-oss-120b) $142; GLM-5.3 claim checks (Z.ai API) $390. The old $730 assumed GLM-5.3 claim checks at no cost; they now run on the paid API. The RunPod line rests on P2 timing (pod `q2pr74unxye0mj`, 2026-11-25): one full FreshStack index (`e8b-c512`, 49,506 files) took 5.65 h; 2,747-file samples gave 0.20 to 0.31 s per file. The nine FreshStack indexes plus the `e4b-c1024` rebuild project to about 45 pod hours (about $40), with each sample rate scaled by 1.33, the full-to-sample ratio measured on `e8b-c512` before the compaction fix `784e478c`. With that fix the build should be faster (not yet measured on a pod), so the figure is conservative. These builds ran with file-type routing on (amendment A13). With routing off, the 600-file check gives 6.1% fewer chunks and 0.4% fewer embedded tokens, so the figure still holds as an upper bound.
- **Ceiling (amended 2026-11-25).** **$1,716** (was $975), pods and hosted calls together: the estimate plus $594 reserve (RunPod reserve for 3 times slower reranking $230; RunPod repeat runs, 10%, $64; price changes, about 10%, $150; failed calls rerun, 10%, $150). RunPod share $704; hosted share $1,012. The OpenRouter key carries a credit limit for the OpenRouter roles only (amended 2026-11-26, pre-freeze, owner; `plan.json` amendment A15): the hosted share $1,012 minus the $390 GLM-5.3 line, **$622**, so an OpenRouter overrun ends in a clean `out_of_credit` stop. GLM-5.3 runs on the owner's Z.ai API key, outside that limit; each run records its GLM-5.3 calls, the Z.ai billing export gives their tokens and cost, and the budget checks count them. The Z.ai endpoint is pinned by SHA-256 and is never printed. The checks, run guard, drop order and stop rule are unchanged (`plan.json` amendment A8).
- **Checks**: before the freeze (test pod extrapolation), on the build pods after the search stage, and at each stage end while the replicate pods run. Each projection uses billing and measured rates only, never scores. Money spent is the sum of the `usd` values of the provider billing rows, each row given as `{provider, usd}`. A projection reaches the ceiling when it is $1,716 or more (amended 2026-11-25; was $975). A budget tool writes each projection to `budget-check.json` and each applied drop step to `drops.json`. The join of stage outputs, the label sampler and the report read the drop record.
- **Run guard.** A main stage refuses to start while `plan.json` `frozen` is empty, and refuses a dirty tree. A pre-freeze run needs an explicit flag. Like every run, it appends one line to `output/run-records.jsonl` (the repository rule), and that line carries `prefreeze: true`. A smoke run (a run with named questions, `--qids`) also appends one line, and that line carries `smoke: true`. The main join and every main-run check ignore lines with either field. A smoke join counts a `smoke: true` line as its run's record. Each run record holds the SHA-256 of this file. Every stage key and every done-marker also hold the run mode (`main`, `prefreeze` or `smoke`). A `--resume` with another run mode than the saved key refuses with exit code 2, so a main run never accepts a pre-freeze or smoke row as done. Every stage that reads an index (search, answer and judge) checks, before its first query, that the index's ingest done-marker holds the configuration its own key expects: the settings of `<index>-roff-hon` with no answer host and no judge. A difference stops the stage with exit code 2 and names each field. A main run also requires an index built by a main run. The oracle stage does not search, so it does not check the index.
- **Drop order at the ceiling** (results-blind, applied in order, each step recorded with the projection that triggered it): (1) Legal RAG Bench answer generation; (2) the length-controlled check; (3) the closed-book run with the RAG prompt; then stop. The owner approved this order on 2026-11-14. Step 1 also removes the 50 Legal correctness labels (section 11.2: correctness sample 150, L1 700, L2 700 in the full plan, 315 at the staged first stage or 630 under the A18 plan). After drop step 1 is recorded, the answer stage on Legal RAG Bench sends nothing, writes no file and exits with code 0; the analysis writes the Legal answer rows 12 to 19 as `dropped` and still computes the Legal search rows 1 to 11. Without a drop record, a dataset with no answers stops the analysis. E1 is not in this order: it has its own ceiling (P16). No confirmatory item is dropped by choice. If the closed-book RAG-prompt run is dropped, the contamination sensitivity (section 13) uses the own-knowledge closed-book run alone, and the report says so.
- **Stop rule.** The run is complete when every search setup has its run, every answer setup and dataset has 3 runs, the closed-book, oracle and length-controlled runs are done, G1 to G3 are checked, and every Ragas and checker row is judged or counted. A run that finishes every confirmatory item after one or more drop steps is "complete with registered drops": each drop is a numbered deviation (section 20). A run is "incomplete" only when a confirmatory item is missing. The run stops early only when the preflight fails, an execution-integrity gate (G1 to G3, section 15) fails, or a projection reaches the ceiling after the last drop step. A failed outcome-validation gate (faithfulness or correctness, section 11.2) does not stop the run: its rows stay in their families as "not testable" (p = 1), and the rest of the run continues. The classifier gate is not one of these stop conditions: gate 3 runs after the freeze, and claim-kind results stay unused until it passes (section 11.1).

## 18. What Experiment 35 fixes for Part 2 and E1

## 20. Deviation policy

## 21. Reporting

- Decisions per row and per hypothesis, estimates with unadjusted 95% intervals, the SESOI reading of each interval, and the gated rows marked "not testable".

## 22. Limitations

- Scope S: one model family at Q8_0 on llama.cpp, English only, no query instruction, one dataset per domain, one hosted answer model behind an ID that may change.
- The reranker's default instruction is a web-search instruction, applied to finance and legal text.
- Incomplete relevance judgements: unjudged units count as not relevant (Zobel 1998; Buckley and Voorhees 2004). FreshStack qrels came from pools that included BM25 and fusion systems, which can favour hybrid search; the fixed audit of section 11.3 measures how far, but cannot remove it. The BioASQ mini corpus is built from gold passages of many questions, so a passage gold for another question is unlabelled here. Most FinanceBench questions have one gold page, while figures often repeat on other pages.
- BioASQ is split by question, so some gold passages are shared across halves.
- Chunk size is a cap, not the realised length; BioASQ and Legal chunks barely change with it, and on FinanceBench a page caps chunk length.
- H6 and H7 use different endpoints on FinanceBench and FreshStack, so the both-datasets rule asks for the same sign from two measures.
- The H7 interaction is defined on each metric's own bounded scale; a ceiling can create or hide it.
- The relevance audit estimates the H3 judgement bias at ranks 1 to 3 only, and only from arm-exclusive unjudged units. It is an estimate, not a bound. It does not cover an unjudged unit in the top 3 of both arms at different ranks. It gives no estimate for H1, H2, H4 or H5.
- H8 faithfulness is checker-measured, and the checker sees longer passages at bigger chunks; the differential-error rule and the length-controlled check address this only in part.
- The primary faithfulness measure checks cited factual claims only. An answer can add uncited facts without losing faithfulness; the uncited-segment share and the sensitivity analysis of section 6 show how much this happens.
- H8b is conditional on reranker on and hybrid on at the chosen sizes.
- The answer model may have seen benchmark text in training; the closed-book runs bound this only in part.
- One index build per cell.
- `resent_calls` counts harness-level resends only. Transport retries inside the client libraries, bounded by the pinned library defaults, are not counted. Cost comes from provider billing, so it is not undercounted.
- The answer model sees the assembled evidence. Assembly removes overlap text between neighbouring kept chunks, so the assembled evidence can be shorter than the cut total of section 3. H8b therefore fixes the pre-assembly budget, not the model-visible evidence, and does not separate chunk size from context length.
- FreshStack corpus rows are byte spans of files, so a Markdown row can start or end inside a code fence, and its headings can then be read wrongly. If the fence fallback of section 4 applies, a `#` comment in a code row is read as a heading.
- Ragas 0.4.3 runs through a custom adapter, not the stock Ragas client. The adapter text is hashed (P13) and named in the methods.
- L1 is an OMRS author.
- The model labeller runs once, in an interactive session with no fixed seed or temperature, so its labels may not repeat exactly; they are released.
- Labellers are not domain experts in finance, software or biomedicine. Every label is judged against the cited text or the dataset's reference answer, never against outside knowledge.
- Classifier gate 3 has about 33 claims per core dataset, so it passes or fails on the pooled sample; per-dataset agreement is reported with intervals only. The classifier failed two development rounds before its prompt was fixed (section 11.1).
